## 1. 目标与成功标准

本轮让维护者能够从最终发布素材复现动画、定位播放问题，并让下载发布包的用户按照随包说明完成校验和安装。

用户已要求基于当前项目审查制定 Spec。推荐顺序为：修复发布包与校验规则 → 建立播放预览及当前 Codex 行为证据 → 按证据优化少数动作。本文件确定拟议范围与验收标准；不视为实施计划或发布授权。

成功标准：

- ZIP 和 tar.gz 包均可脱离仓库，按照随包 README 完成包校验及隔离安装。
- 校验器、Windows 安装器和 POSIX 安装器对约定的 manifest 错误给出一致的接受／拒绝结果。
- 预览直接使用最终 WebP，覆盖九个标准状态、neutral 槽与 16 个注视方向。
- 每个重点动作有保留或调整的结论，并能追溯到具体素材和播放配置。
- 自动测试、预览验收、真实应用验收分别记录；其中一项通过不能代替其他项。

## 3. 方案选择

| 方案 | 收益 | 代价与限制 | 决定 |
| --- | --- | --- | --- |
| 仅修包与校验器 | 最快解决已复现问题 | 无法解释或评估动作播放体验 | 作为第一阶段 |
| 修包＋版本化播放预览＋定向优化 | 将工程缺陷与播放体验关联到同一份最终素材 | 需要小型预览工具及播放配置证据 | 本 Spec 推荐 |
| 全量重画所有动作 | 可统一调整美术 | 成本高，容易损失已通过的角色一致性，且不能解决应用触发限制 | 不纳入 |

不新增桌面应用框架、前端构建链或远程服务。预览使用本地静态 HTML/CSS/JavaScript，由 Python 工具生成自包含 HTML，可直接在浏览器打开。

## 4. 范围与保留约束

### 4.1 必须交付

- 自包含的发布包内容与中英文安装／校验说明。
- 明确的 manifest 与图集校验规则，以及一致性回归测试。
- 集中管理的已批准图集哈希和发布前一致性检查。
- 基于当前素材的播放预览工具、版本化播放配置和逐行动作评估表。
- 针对当前 Codex 版本的行为调查记录与独立的应用内验收记录。

### 4.2 按证据启动

重点评估 `waving`、`jumping`、`failed`、`running`（工作）和 `review`。仅在评估结论为 `ADJUST` 后生成替代素材；`RETAIN` 不触发重画，`UNVERIFIED` 先补证据。

16 个注视方向本轮进行回归检查。已有七个中间方向的轻微警告不自动升级为重画任务；只有发现方向反转、明显跳变、裁切或身份漂移才进入修复范围。

### 4.3 不纳入

- 修改 Codex 应用二进制、强制改变其触发机制或重复次数。
- 新增语音、对话、联网、自动更新或新的 Pet 身份。
- 全量重画、扩展图集协议、迁移到云端 Pets 服务。
- 与本目标无关的安装器重构或额外的平台支持。
- 本 Spec 编写阶段的实际安装、发布、推送或美术生成。

角色身份遵循现有 [identity lock](../../production/identity-lock.md)。包 ID、显示名、v2 布局及 192 × 208 单元格保持不变。代码／文档与美术素材的权利边界继续以根目录 `LICENSE`、`NOTICE.md` 和 `THIRD_PARTY_NOTICES.md` 为准。

发布包不包含 pytest、开发测试、全部历史 QA、生成源文件或实现预览器的开发工具。用户校验需要 Python 与 Pillow；安装器继续保持现有依赖范围：Windows 使用 PowerShell，POSIX 使用 Python 3 和现有哈希工具。

### 5.2 素材锁定文件

`release-assets.json` 位于仓库／解压根目录，结构固定为：

```json
{
  "schemaVersion": 1,
  "petId": "ellen-joe-pixel",
  "spritesheetSha256": "c6f4ed31f670e00cda1b596f35372b3b60ba5a6cb94dbd6e049b2e1950fc15e6"
}
```

Windows 和 POSIX 安装器读取同一文件；取消两个脚本内各自维护的哈希常量。哈希统一使用小写 64 位十六进制。锁定文件缺失、结构无效或哈希不匹配时，安装器在修改安装目标前返回现有无效源退出码 `3`。

构建器读取锁定文件并验证最终字节，不自动把任意当前素材认定为已批准。更换图集时，在素材验收后显式更新该记录。该文件用于一致性检查，不宣称提供数字签名或独立的来源认证。

实际安装到 `pets/ellen-joe-pixel` 的内容仍只有 `pet.json` 和 `spritesheet.webp`；锁定文件属于发布工具，不扩展 Codex manifest。

### 5.3 构建与包内验证

## 6. 校验契约与安装器一致性

### 6.1 Manifest

顶层必须为 JSON 对象。现有字段保持兼容：

| 字段 | 必须满足 |
| --- | --- |
| `id` | 字符串，精确等于 `ellen-joe-pixel` |
| `displayName` | 字符串，精确等于 `Ellen Joe Pixel` |
| `description` | 非空白字符串 |
| `spriteVersionNumber` | JSON 整数 `2`；拒绝 `2.0`、`2e0`、字符串及布尔值 |
| `spritesheetPath` | 字符串，精确等于 `spritesheet.webp` |

所有重复顶层键均拒绝，不采用“最后一个值生效”。未知且不重复的顶层字段允许存在，以保留当前扩展容忍度。字段名及固定字符串比较区分大小写。保留对 UTF-8 BOM 的兼容读取，使 Windows PowerShell 5.1 写出的有效 JSON 不因编码差异被误拒绝。

Python 校验器与两种安装器对同一组 manifest fixtures 应有一致判定。覆盖有效对象、重复键、错误类型、大小写差异、缺字段、空白描述、BOM 和不重复的未知字段。

### 6.2 图集结构

- 根据文件内容验证真正的静态 WebP，拒绝其他格式改名和动画 WebP。
- 检查解码尺寸、透明通道及单元格占用；不能依靠转换为 RGBA 掩盖输入缺少透明通道。
- 尺寸固定为 1536 × 2288，8 列 × 11 行，单元格 192 × 208。
- 已占用格数为 `(7, 8, 8, 4, 5, 8, 6, 6, 6, 8, 8)`。
- 第 0 行第 0–5 列是六帧 idle；第 6 列是 neutral/look 回退槽；第 7 列为空。neutral 槽不能作为 idle 第七帧播放。
- 所有使用格必须有可见像素，所有未用格必须完全透明；只检查占用不代表动作语义或视觉质量通过。

### 6.3 结构有效与批准字节分开

`validate_pet.py <pet_dir>` 保留原有结构校验入口；新增可选 `--asset-lock <path>`，同时验证批准哈希。成功返回 `0`，校验失败返回 `1`；错误输出应指出字段或行列。

安装器始终验证锁定哈希，因此无需新增 Pillow 依赖来重复解码已批准图集。构建和发布检查必须同时执行结构与哈希校验。保留安装／卸载现有退出码、精确目标处理、备份位于发现目录之外和失败回滚行为。

## 7. 播放预览工具

### 7.1 输入与交付形式

开发入口拟为 `scripts/build_preview.py`，读取待验收的最终 WebP 和播放配置，将素材与配置嵌入自包含 HTML。默认输出到明确的临时位置；允许调用者指定输出文件。

不读取旧 GIF 作为播放真值。页面展示素材 SHA-256、配置来源、配置适用的 Codex 版本及验证等级。缺图、无效配置或不兼容图集应明确报错，不显示上次成功的素材冒充当前输入。

工具实现保存在仓库；可再生成的 HTML 与浏览器缓存保存在临时目录。经挑选的验收截图、评估表和播放配置可以提交到版本化 QA 目录。

### 7.2 最小交互

- 选择九个标准状态、neutral 和 16 个注视方向。
- 播放／暂停、重新播放、上一帧／下一帧；显示当前行、列和播放阶段。
- 单轮模式播完后停在末帧；循环模式按选定序列持续播放。
- 单独的 Codex 配置模式按已核验规则执行重复、回到 idle 和中断行为。
- 原始 1× 与整数 2× 放大，使用像素化渲染；提供浅色、深色和棋盘格背景。
- 支持 0.5×、1×、2× 速度；验收以 1× 为准，其他速度仅辅助分析。
- 切换动作从新动作首帧开始；手动切换与应用状态事件模拟在界面上明确区分。
- 页面隐藏时暂停；恢复后保留进度，避免后台计时补偿导致跳帧。标注这是预览工具行为。

不增加时间轴编辑、绘图、导出视频或自定义动画编排功能。

### 7.3 播放规则来源

配置文件区分两个用途：

| 类型 | 来源 | 允许的声明 |
| --- | --- | --- |
| 诊断配置 | 明确写出的帧时长及序列参数 | 用于观察素材，不能称为真实 Codex 行为 |
| Codex 配置 | 当前安装版本的代码证据和／或实际观察 | 复现已确认的行为；必须标注证据等级与版本 |

诊断模式默认每帧 160 ms，仅用于检查帧顺序和形变，不作为目标应用节奏的结论。

Codex 配置至少记录：应用版本、采集日期、来源定位或文件指纹、每状态帧序列及时间、重复与结束策略，以及已确认的状态优先级、中断和注视触发规则。代码检查证据标记为 `STATIC_VERIFIED`；实际观察证据标记为 `APP_OBSERVED`。

未知规则必须显式标记为未知。缺少播放序列、时长或重复策略时禁用 Codex 播放模式；仅缺少状态优先级等事件规则时允许播放已确认序列，但禁用相应事件模拟。不得悄悄沿用旧版本数值补足缺口。

事件模拟只实现已经确认的规则，至少验证：idle → work、work → waiting、work → failed、work → review，以及动作完成后的实际去向。具体优先级和是否从头重播由证据决定，不在 Spec 中预设。

## 8. 动作评估与有条件修复

### 8.1 评估表

九个标准状态均填写记录，重点状态先处理。每行包含：状态、素材哈希、播放配置、1× 观察、首尾衔接、与 idle 的切换、角色一致性、语义判断、结论、证据路径和验收者。

结论仅使用：

- `RETAIN`：当前证据下保持素材。
- `ADJUST`：记录了具体可见缺陷，进入定向修复。
- `UNVERIFIED`：缺少所需播放或观察证据；不能算通过。

### 8.2 重点观察项

| 状态 | 观察与通过条件 |
| --- | --- |
| `waving` | 能辨认为招手；重复时手部和身体衔接自然，回 idle 不突变 |
| `jumping` | 蓄力、离地、顶点、下降和落地顺序可辨；不出现无意的二次起跳、形体缩放或落地跳变 |
| `failed` | 失败情绪明确；若应用重复播放或切回 idle，不能出现明显的姿态重置抽动 |
| `running` / `review` | 工作与检查的主要动作可区分；不能仅凭标签判断状态 |
| 注视方向 | 保持顺时针方向、跨行衔接和身份一致；原有轻微警告单独保留 |

视觉判断由验收者在 1× 查看并记录理由，不用像素差阈值代替。未确认应用实际展示的缺陷，只能标为预览中观察到的问题。

### 8.3 修复边界

修复保持当前像素风格、全身比例、配色、尾部连接及各状态道具规则。不新增特效或协议外帧数。美术修改以现有批准素材为参考，优先替换完整问题动作行。

先保留基线文件及哈希，再生成候选；候选通过结构、视觉和播放评估后才替换正式素材。未修改行的解码像素应保持一致；最终 WebP 重新编码后重新校验并更新哈希、预览、QA 和锁定文件。不得以先更新哈希的方式绕过候选验收。

如果所有重点状态均为 `RETAIN`，允许以原图集交付工程优化和验证工具；不为满足“优化”名义制造素材改动。

| AC-11 | 应用内验证 | 记录实际 Codex 版本及安装哈希，确认选择器中唯一条目、idle、work、review，并观察可安全触发的重点状态 |

AC-06 是隔离安装测试；AC-11 才是真实用户应用验证。截图只能证明画面存在，循环和切换结论需要录屏或有步骤、观察结果及验收者的人工记录。

应用内不能触发某状态时，记录该状态为 `NOT_RUN` 并注明原因，不制造失败任务或其他业务动作来获取画面。无法操作应用时，可以交付工具及预览结果，但验收记录必须保留限制，不标记全部完成。

最终 QA 分别报告 `PACKAGE`、`INSTALLER`、`PREVIEW`、`APP` 四个维度，状态使用 `PASS`、`FAIL`、`NOT_RUN`，并逐项记录缺口。静态检查和自动测试不能把 `APP` 改成 `PASS`。

本轮目标是四维通过。若应用访问限制导致 AC-11 未完成，公开发布是否接受这项缺口由 Boss 在具体交付物上决定；默认不把旧版豁免当作本轮豁免。声明仅覆盖实际检查的平台和版本。

## 10. 交付物与阶段顺序

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| A：包与校验修复 | 自包含档案、统一 manifest 规则、素材锁定文件及回归测试 | 已知复现项闭环，原包保持兼容 |
| B：规则与预览 | 当前运行时证据、播放配置、预览工具、现有素材评估表 | 素材与播放规则可追溯，问题行可明确定位 |
| C：定向素材修复 | 仅有必要时产出候选图集和对照证据 | 问题行通过，其他行无回归 |
| D：验收与发布准备 | 四维 QA 记录、双语说明、发布说明、档案与校验和 | 验收缺口明确；发布执行另行处理 |

建议持久化文件位置：

- `release-assets.json`、`requirements-validator.txt`：发布支持文件。
- `scripts/build_preview.py`、`scripts/preview/`：预览生成入口与静态模板。
- `qa/playback/v0.1.3/`：播放配置、运行时证据、逐行评估和本轮 QA 记录。
- `docs/releases/v0.1.3.md`：版本说明，在版本号最终确定后使用。

这些是模块和交付物边界，不是逐步实施计划。编写实施计划时再确定函数划分、测试文件和提交顺序；本 Spec 不预先指定 subagent、模型或执行方式。

## 11. 风险与处理决定

- **应用升级导致规则变化：** 配置以明确版本为边界，升级后重核；旧配置可以保留为历史诊断。
- **预览与应用调度不同：** 预览只复现已确认行为；应用验证独立验收。
- **重画导致角色漂移：** 先用现有素材评估，仅替换确定存在问题的行，并保留基线对照。
- **发布包扩大：** 只包含用户流程需要的预览图和工具依赖，完整开发 QA 留在仓库。
- **历史文档与本轮证据混淆：** 保留旧记录，新记录使用版本目录及素材哈希，不覆盖历史验收结论。
